## 3 ★★ 单位坑（实测，会毁掉整份件）

**SketchUp 的 Ruby API 里，裸数字一律是英寸。** 实测：写 `add_face([[0,0,0],[10_000,0,0],…])`
再 `pushpull(-4_000)`，导出的 OBJ 量出来是 **254000 × 203200 × 101600 mm**
（= 10000 × 8000 × 4000 **英寸**）—— 大了 **25.4 倍**。

菜单里的 `UnitsOptions / LengthUnit = 2`（毫米）**只管显示**，管不了 API 里的数字。

- **手工建模不受这条影响**（你在界面上按显示单位敲 `10000` 或 `10000mm` 就行）。
- **一旦用脚本建**，必须显式换算，例如 `10000.mm`，或乘 `25.4`。
- 导出时以 OBJ 头部的 `# File units = millimeters` 为准，别信记忆。

## 4 ★★ 朝向坑（两个导出器不一样，实测）

同一个 10000×8000×4000（英寸）的盒子，SU 2023 导出的两份件：

| 导出器 | 头部声明 | 实测朝向 |
|---|---|---|
| **OBJ** | `# File units = millimeters` | **Y 朝上** —— 高度落在 Y；三个方向尺寸 254000 / 101600 / 203200 mm |
| **DAE** | `<unit meter="0.0254" name="inch"/>` + `<up_axis>Z_UP</up_axis>` | **Z 朝上**、且声明单位是**英寸** |

⇒ **同一个模型，两份件，朝向和单位都不同。**

★★ 而且 **OBJ 的单位不是常数，是导出对话框里的选项** —— 同一个 SU 2023，
本仓探针量到 `# File units = millimeters`，而 gym3d 那条早先的链量到的是
`# File units = inches`（还得在 Blender 里 `global_scale=0.0254`）。
两次都是真的，差别只在当时的导出设置。

**所以别信「SU 导出就是英寸」或「就是毫米」这类说法** —— §1 要求你在 `EXPORT.md`
里写明 **导出器 + 单位 + 导出时刻**，这一行省掉，下游就只能猜，而猜错是 25.4 倍。

> 为什么非写不可：2026-10-13 已经因为这一类的朝向错出过一次事故 ——
> 参照件当初按内部 Z 朝上写盘，谁按 glTF 规范（+Y up）读谁就把整栋放倒，
> 三视图里正立面与俯视**对调，且两张还都「看着挺像」**。见 `构件清单.md` §6。

## 5 能不能后台跑（实测答案）

**能无人值守，但没有无头模式**（窗口会闪一下，全过程不用点）。

```bat
"C:\Program Files\SketchUp\SketchUp 2023\SketchUp.exe" "<任意一个已存在的 .skp>" -RubyStartup "<脚本>.rb"
```

两个坑，都是实测踩出来的：

1. **必须给一个「要打开的文档」参数。** 否则**欢迎屏会挡住启动**，
   脚本一行都不执行（`-RubyStartup` 本身是好的）。
2. **API 常量名是 `Sketchup`，不是 `SketchUp`。** 写 `SketchUp.active_model`
   报 `uninitialized constant SketchUp (Did you mean?  Sketchup)`。
   脚本里用 `defined?(SketchUp) ? SketchUp : Sketchup` 最稳。

实测那次跑通了：脚本进入（`ruby=2.7.2`）→ 建盒 → 存 `.skp`（588795 字节）
→ 导出 OBJ（60408 字节）/ DAE（81978 字节）→ 自己 `quit`，进程退出，全程零点击。

3. ★★ **SU 是单实例**：上一个实例还没退干净就再启一个，新实例会把参数交给旧的就退出，
   脚本**一行不跑也不报错**（看着像「参数没生效」）。启动前先 `Stop-Process -Force` 并等 5 s
   —— 见 §7 第 5 条（和上面第 1 条**症状同形**，别混）。

以我这边跑通的命令（bash 单行，路径含中文；**别用 bash 直接调 `.exe`**，实测返回 `rc=127`）：

```
powershell -NoProfile -Command "& 'C:\Program Files\SketchUp\SketchUp 2023\SketchUp.exe' 'D:\项目\cdut3d\rebuild\06_su\c006_su.skp' -RubyStartup 'D:\项目\cdut3d\rebuild\06_su\su_step2_build.rb'"
```

## 6 正式件的判据（`J-10.8-02`，待写）

**关键约束：它不许读 `rebuild/05_build/build.json`。** 那份是我自己 Python 生成的，
拿它当参照物 = 同源盲区（铁律 137/187/192）：参照物和被测量出自同一个约定，
约定错了它也看不见。

所以正式件的判据要**另找独立参照**：

- **朝上轴**：拿件的**平面 footprint** 去对 DXF 里的 `4.2墙体` 线脚 —— 哪个平面（XY / XZ / YZ）
  与 DXF 墙脚吻合，哪个轴就是高度轴，**不预设** Y 或 Z。
- **尺度**：同一份 footprint 与 DXF 的 mm 尺寸比，定出 **单位**（1 / 0.001 / 25.4 三种都要能分出来）。
- **层数/层高**：DXF 是 12 张平面图 ⇒ 地上 11 层 + B1；逐层高度**不在这里写数**，
  一律取 `rebuild/构件库/参数.json::构件.共用/层高`（当前 **3.5 m**，2026-10-15 用户定的口径）。
  ★ 这里原写「逐层高度对 **4.0 m 档**」，层高改档后就成了一句**静默过期**的话
  （铁律 018/174：同一个数写在两处，两处一致也证明不了它对）—— 所以改成**只指真源、不抄数**。
- **件数**：门块 `$DorLib2D$*` 754、柱块 `_FZHK` 1206 + `_YZHK` 104、`上`/`下` 136 ——
  这些**在源件里是按名字可点名的**，是量正式件的客观分母。
- **反证**：判据必须能对**已知坏的件**报红（例如把高程轴换成平面轴、单位乘 25.4）。

## 8 ★★ 第 4 批（顶部三件）跑红记：两个缺陷都在**我们的输入**里

补建女儿墙 / 顶楼楼梯房 / 7→8 台阶屋面时，头一次跑 SU 当场报
`FACES built=4 fail=1`、`BBOX_mm size=[129300.0, 84000.0, 90500.0]`。两处都不是 SU 错：

1. **两个原点**（铁律 174 那一类）。记录里的 `z` 约定是**相对本层底面**
   （SU 脚本写 `zbase + pr["z"]`，`zbase = z0*1000`），而第一版的附属件写进去的是**绝对**标高
   ⇒ 女儿墙落到 84000 mm（40 m 层底 + 44 m 绝对）、台阶屋面落到 51880 mm。**总高 50.5 m ⇒ 90.5 m。**
   处置：`export_contours.py` 加 `_rel_z(name, z_abs_mm)`，减本层 `z0` 并当场上界检查
   （相对标高必须落在 `[0, 层高]` 内，越界直接抛）。
2. **零长边**。`round(…, 1)`（0.1 mm）把两个不同的坐标**圆成同一个数**，
   环上出现连续重复点。★ shapely 判 `is_valid / is_simple` **全 True**（重复顶点不算自交），
   **SU 却建不出长度 0 的边** ⇒ 那条多边形**静默**少一张面（2 条只成了 1 条，其余全部正常）。
   处置：`_dedup()` 只去**相邻**重复点、闭合点保留；12 层 8591 个环/洞重扫，零长边 0 处。

**重跑为什么还需要一个删组脚本**：`su_step2_build.rb` 的续跑规矩是「同名组已存在就跳过」
（这是它**能分批**的原因）。所以已经建错的那三个组必须先按名字删掉，否则重跑会被跳过。
`su_fix_erase.rb` 就是干这个的：名单从 `_erase.txt` 读（**不写死在脚本里**，免得补救代码将来变地雷），
只删不建、删完存盘导出。★ 本次已用完，`_erase.txt` 里的三个名字**已注释掉** ——
**再跑一次那个脚本会把这回建好的组删掉**，除非你确实要重做。

修完重跑：`7层/ROOF_STEP z=27880.0mm`、`11层/PARAPET z=44000.0mm`、`11层/ROOF_STAIR z=44000.0mm`，
`FACES built=5 fail=0`、`BBOX_mm size=[…, 50500.0]`（总高 **50.5 m**，与参照件一致）。
