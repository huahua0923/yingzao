## 6 三维出件与**朝向口径**（`rebuild/05_build/`）

`python rebuild/tools/build3d.py` 出四件：
`c006_white.obj` / `c006_white.glb` / `c006_white.blend`（可打开精修）+ `build.json`（每层实测账）。
三视图 `python rebuild/tools/render3d.py` ⇒ `c006_{iso,front,top}.png`。

| 项 | 口径 |
|---|---|
| **脚本内部** | 一律 **Z 朝上**（高度在 z）—— 与 `build.json` 里的 `z0`/`z_measured` 一致 |
| **出件（OBJ/GLB）** | **Y 朝上** —— glTF 规范规定 **+Y up**；OBJ 无正式上轴，但 SU / Blender 导入默认也是 Y-up |
| 怎么做到的 | 写出前整场绕 **X 转 −90°**（`Scene.apply_transform`） |
| ★ 两条路落在**不同地方** | **OBJ**：trimesh 把旋转**烘进顶点**；**GLB**：顶点一个字节没动，旋转写在 **76 个节点的 `matrix`** 里 |
| 打开 `.blend` | Blender 是 Z 朝上，导入 glTF 时**替我们转回去** ⇒ 打开就是正的 |

**★ 本节口径只对上面这份「参照件」负责。** 正式件（你在 SketchUp 里建的）另有一套，
2026-10-13 实测过它的导出行为 —— 同一个盒子，**两个导出器朝向就不同**：

| SU 导出器 | 声明 | 实测 |
|---|---|---|
| OBJ | `# File units = millimeters` | **Y 朝上** |
| DAE | `<unit meter="0.0254" name="inch"/>` + `<up_axis>Z_UP</up_axis>` | **Z 朝上**、声明**英寸** |

另有一条会毁件的：**SU 的 Ruby API 里裸数字是英寸**（写 `10000` 建出来的是 254 m，
大了 25.4 倍；`LengthUnit=mm` 只管显示）。完整交接见 **`rebuild/06_su/README.md`**。

**为什么专设这一节**：2026-10-13 出过这个坑 —— 出件写成 Z 朝上（照内部坐标原样写盘），
谁按规范读谁把整栋**放倒**，于是 `c006_front.png` 画的是俯视、`c006_top.png` 是正立面，
**两张对调还「看着挺像」**。判据 `J-10.8-01` ⑫ 专盯这一条，量具是**两份互不同源**的读者：
字节层读 GLB（**走节点树累积 `matrix`**）+ 纯文本读 OBJ 的 `v` 行；`render3d.py` 里另有一道
自检（件进 Blender 后高度必须落在 Z，否则 `ORIENT_FAIL`、**一张图都不出**）。

> ⚠ 若你日后**手工**改了 OBJ/GLB（而不是重跑 `build3d.py`），这条口径可能已经过期 ——
> 那两份是**生成物**，请以重跑脚本的结果为准。
