# 孪生血缘链与新鲜度

> 域：`twin`。本域最要紧的一条：**链条上每一环都要能说出「我从哪来、我比我的输入新吗」**。
> 说不出来的那一环，就是下次「看着没问题、其实全是旧的」会发生的地方。

## 关键结论

- **判据的正确形状 = 下游 vs 它的真输入。** 真输入是**生成它的那些文件**，不是中间产物。
  `render_floor_png` 全程读 DXF + profile、**不读** `floors/*.json` ⇒ 拿 floor JSON 当它的
  新鲜度判据是错的：floors 天天改，会把本来有效的预渲染图一律判旧，退回请求期现算。
- **只判「文件在不在」等于永远不刷新。** 实测 2026-09-14：全库 49/49 栋的 `plans/recog_floor*.png`
  都停在 2026-09-11 那版，而 DXF 之后重出过 —— 用户看到的「实际那张图」一直是旧的，
  不跑 `--force` 永远追不上。
- **同一判据两份实现，而且不会自己红。** 请求期判据与预渲染的 `is_fresh()` 是同一套，
  注释自己写着「改一处要改两处」。这类双源要靠人记 —— 那就等于没记。
- **同一份文件里，模块 docstring 与函数 docstring 互相矛盾**：`prerender_floor_png.py`
  开头仍写「增量的判据 = **不比本层 floor JSON 旧**」，而 120 行之后的 `is_fresh` 已改成
  DXF / profile。**实现是新的，开头那句结论是旧的** —— 读开头那段的人会照着错的做。
- **两种新鲜度口径并存**：内容指纹 `sha12`（正确形状）与 `mtime + size`（便宜，缓存键在用）。
  mtime 会被 `cp -p` 原样带走 ⇒ **「从备份恢复」这个动作不会让缓存失效**。
  同族的实测结论：按 mtime 判模型陈旧**漏了 28/48 栋**。
- **缓存键必须覆盖被缓存的值真正读到的每一份文件。** 少放一份进去，
  就会出现「改了它、页面还显示旧值」而且**不报错**。
- **三个数都对，口径不同**：「95 个楼栋目录」「管线 49 栋」「源目录 105 个 DWG」——
  三个全是对的，缺的是**写下来的是哪个口径**。凡是报「全库几层/几栋」，必须同时说是哪个口径。
