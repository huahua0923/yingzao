# cdut3d 系统评估与清理

> 评估日期：2026-10-20  
> 评估方式：读代码、读方案、跑页面、复跑判据、统计磁盘与引用关系。  
> 原则：删得回来才删；量不到就写没量到，不写成通过。

## 1 总体判断

cdut3d 已经具备一条真实的“图纸 → 识别 → 重画 → 建件 → 模型包 → 浏览器查看”生产链，也有较完整的判据体系。它现在的主要问题不是“功能太少”，而是：

1. **一个仓库同时承担生产、质检、交付、展示、运维五种职责**。
2. **展示面和管理面混在同一个无认证 HTTP 服务里**，直接上公网风险高。
3. **大量历史工件、过程证据和可重出中间件混在工作树里**，导致目录看起来庞大，但真正能删的缓存并不多。
4. **判据很多，但台账有陈旧读数**；绿数不能直接当今天的结果。
5. **没有发布边界**：没有统一的版本包、清单、锁文件和回滚入口。

## 2 当前架构事实

- 唯一运行进程：`workbench/server.py`，默认 `127.0.0.1:8150`。
- 服务同时托管静态页面与 API，不是真正的前后端分离。
- `/admin`、`/pipeline`、`/compare`、`/criteria` 由同一进程返回。
- 前端通过同源 iframe 组合：首页、工作台、流程台、对照、判据。
- 大模型来自 `packs/` 与 `过程/_layers/`；展示页并不自己生成几何。
- 本地生产依赖 AutoCAD、Blender、FreeCAD、RealityCapture/COLMAP 等 Windows 工具。

## 3 系统缺陷

| ID | 级别 | 缺陷 | 证据 | 处置 |
|---|---|---|---|---|
| A01 | P0 | 公网部署时没有认证与授权 | 所有路由同进程；写接口只做同源检查 | 生产中管理端必须加 Nginx 基础认证/VPN，展示面只读 |
| A02 | P0 | 没有 HTTPS 与安全边界说明 | 服务本身是 HTTP，只绑本机 | 证书由 Nginx 终止；新增 `docs/部署拓扑-cdut3d.md` |
| A03 | P1 | 大 GLB 原实现整件读入内存 | `_mount()` 原来 `read()` 后发送 | **已修**：流式发送 + ETag；139 MB 文件不再按并发复制进内存 |
| A04 | P1 | 生产域名下写请求会被误拒 | `_same_origin()` 只认 localhost/127.0.0.1 | **已修**：改为同 Host 比较，并支持 `CDUT3D_ALLOWED_ORIGINS` |
| A05 | P1 | 台账可能陈旧 | 40 条中 37 绿、1 红、2 没量到；复跑 `J-09.2-A1` 已转绿 | 每次发布前统一重跑并刷新 `_ledger.json` |
| A06 | P1 | 没有依赖锁与自动检查 | 根目录没有 `pyproject.toml`、`uv.lock`、CI | **本次已补**，但仍需在干净机器上验证 |
| A07 | P1 | 判据 `J-09.1.1-viewer` 的 H 条选错刺激像素 | 复跑 rc=4：指针打不到模型 | 用 `过程/_scratch/probe_pick.py` 重选像素，不能把 rc=4 写成通过 |
| A08 | P1 | `J-10.10-10` 给不出竖向锚 | 交付侧 `7层/ROOF_STEP`、`11层/ROOF` 找不到 | 需要补 CAD/实测层高或明确允许“无竖向真值”口径 |
| A09 | P2 | 无访问审计与结构化日志 | 服务只打印错误；无 access/audit 落盘 | 生产由 Nginx 记录访问日志；写操作后续加审计表 |
| A10 | P2 | 单体代码偏大 | `workbench/server.py` 约 1539 行，`pipeline/server.py` 约 980 行 | 先按发布边界拆分，不在此轮做大重构 |
| A11 | P2 | 多处绝对路径与 Windows 工具依赖 | 部分脚本写死 `D:\项目\cdut3d\...` | 本地生产可保留；发布脚本只收相对路径 |
| A12 | P2 | 实景 3D Tiles 尚未接入当前查看器 | 现有查看器主要吃 GLB；瓦片仍由外部体系生产 | 见 `docs/倾斜摄影融合实现方案.md`，先做适配层与同机位对照 |

## 4 生产流程问题

### 4.1 正确的地方

- 本地重算、服务器只展示，边界清楚。
- 每个关键步骤有判据，且很多判据带正对照。
- 模型包有格式规范、稳定 ID 规则、LOD 声明。
- 工作台写参数前有校验、备份、原子替换和回读。

### 4.2 需要收紧的地方

1. **判据读数要按“最近一次实跑时刻”消费**。旧绿不能当今天的绿。
2. **外部程序退出码不可信**。AutoCAD `accoreconsole` 已知会静默或挂死，必须超时 + 回执文件 + 产出物验收。
3. **发布和服务之间缺一条可验证的交接带**。服务器不能直接读开发工作树；应只接收带 `release-manifest.json` 的发布目录。
4. **公共展示与管理写入必须分权**。查看器可以公开，参数修改、重跑、DXF 下载不能公开。
5. **中间件生命周期要分层**。过程证据、可重出中间件、交付件、历史归档不能同权删除。
6. **倾斜摄影与白模要按层合成**，不能把“照片瓦片”直接当可剖切模型使用。

## 5 清理结论

### 5.1 目录体积

| 目录/文件 | 体积 | 性质 | 处置 |
|---|---:|---|---|
| `rebuild/` | 约 2607 MB | 本地生产链、DXF、模型、旧快照 | 保留；按发布批次归档 |
| `_archive_bak_2026-10-20.zip` | 约 1571 MB | `_archive/` 历史备份，17,738 条，压缩包自检通过 | **保留**；不是普通缓存 |
| `过程/` | 约 1132 MB | 实景分层、对照与证据 | 保留；清理只动 `_scratch` 中可重出件 |

| `packs/` | 约 465 MB | 已验收交付包 | 保留；由发布脚本打包 |
| `demo/` | 约 454 MB | 查看器与部分历史控制件 | 保留；`_gen` 有判据引用，不能凭大小删 |
| `_edit/` `_drill/` `_回切_按栋/` | 约 735 MB | 实景主件/回切证据 | **保留**；上一次误删已证明它们是判据输入 |

### 5.2 已确认可删

- 全仓 `__pycache__`、`.pyc`：61 个缓存目录、595 个文件、12,231,005 B（含新生成的 `.venv` 字节码缓存），均为可重出字节码。
- `项目cdut3drebuild_scratchgatebase/`：5 个旧判据文本快照、27,438 B，全仓无引用；已归档后删除。

### 5.3 明确不删

- `demo/_gen/`：被 `J-09.2-A1e` 等多个判据引用，且是旧链证据。
- `过程/_scratch/_bad_packs/`：虽然叫 bad，但可能是缺陷复现证据；先保留。
- `_archive_bak_2026-10-20.zip`：虽然大，但可能是历史目录的唯一完整备份。
- `rebuild/06_su/_archive/`、`rebuild/_archive/`：回滚和判据溯源需要。

## 6 建议的后续分层

```text
src/            代码与规范
releases/       可部署发布包（带 SHA-256 清单）
state/          运行状态、任务、审计、上传
data/           已验收 packs 与实景层
evidence/       闸账、对照、截图、复现材料
cold-archive/   季度归档，可外置磁盘
```

当前不做整仓搬迁，先在发布和备份流程中落实分层；一次性移动大目录的风险高于收益。
