# 倾斜摄影与 cdut3d 融合实现方案

> 依据：`建设方案V3·2026-10-11.md` 的 §4.2、§6.2.3、§7.4、§7.9、§10.8，以及 `规范/实景主件格式-v1.md`。

## 1 现在有什么

- 2024 航拍成果：`F:\理工数据\理工模型-3Dtile\`，约 12 GB、48,701 块瓦片，来自 ContextCapture/OSGB 体系。
- 现有 CDUT 三维查看器：Three.js + GLB 白模，能切楼层、点房间、看构件。
- 实景主件规范：已定义 LOD 前沿、祖先链、坐标变换和回写规则。
- 本地工具：RealityCapture、COLMAP、PotreeConverter、py3dtiles、Blender、GDAL、QGIS。

## 2 为什么现在还没接上

不是“没有数据”，而是缺四段接口：

1. 3D Tiles 还没有作为发布物进入服务器目录。
2. 当前查看器没有加载 `tileset.json` 的渲染器。
3. 白模 EPSG:4544 平面坐标与瓦片 ECEF/ENU 之间还没有正式的锚点变换表。
4. 没有定义远近景分层、LOD 切换、瓦片缓存和失败回退。

## 3 技术路线

### 3.1 渲染器选择

目标是把实景层与白模放在同一个 Three.js 场景里，因此优先：

**Three.js + `3d-tiles-renderer`**

理由：

- 当前查看器已经是 Three.js。
- 房间色块、构件点选、剖切、高亮都依赖同一个场景。
- 实景只作为一层，不另起 Cesium 世界，避免两套相机和两套 UI。

备选：

- Cesium 单独作为“实景对照”页，先验证瓦片质量与性能。
- 若 Three.js 路线的内存或首屏不可接受，再保留 Cesium 作为独立浏览入口。

### 3.2 坐标配准

需要新增 `building_anchors`：

| 字段 | 含义 |
|---|---|
| `building_id` | 楼栋 |
| `easting_m` / `northing_m` | EPSG:4544 平面锚点 |
| `height_m` | 椭球高/项目高程基准 |
| `yaw_deg` | 模型朝向 |
| `tileset_transform` | 16 个数，原样记录 |
| `source` | 来源与控制点 |
| `residual_m` | 配准残差 |

流程：

1. 从 `tileset.json` 读取 `root.transform`。
2. 用 `pyproj` 把白模局部坐标转 EPSG:4544，再转 ECEF。
3. 用至少 4 个控制点求平移/旋转；6 个以上做残差检查。
4. 没有控制点时只报配准偏移，不声称精度。
5. 暂定目标：平面残差 ≤ 0.15 m，竖向残差 ≤ 0.20 m；最终以实测控制点为准。

### 3.3 分层渲染

| 层 | 内容 | 规则 |
|---|---|---|
| 近景 | 白模 GLB | 可剖切、可点选、可着色 |
| 远景 | 实景 3D Tiles | 只读，降饱和、空气透视 |
| 贴地 | 正射/DOM | 只作底图，不参与点选 |
| 附属 | 树、天空、道路 | 后续替换，不混入模型包 |

渲染策略：

- 相机距离近：白模不透明，实景淡出。
- 相机距离远：白模降低细节，实景主导。
- 楼层剖切时：实景层自动隐藏，避免照片墙体挡住室内。
- 点选时：只命中白模与房间，不命中瓦片。

### 3.4 深度冲突

- 白模与实景重叠区使用 polygon offset / depth bias。
- 建筑外立面以白模为准，实景只作背景与屋顶远景。
- 不做“照片瓦片直接套白模表面”，否则会产生双重阴影和接缝。

## 4 本地生产链

```text
原始影像 + POS + 控制点
  → RealityCapture / COLMAP 空三
  → 稠密点云
  → 网格 + 纹理
  → DOM/DSM + 控制点检查
  → py3dtiles / PotreeConverter 切片
  → tileset.json + 瓦片包
  → 发布清单
```

纪律：

1. 原片不搬、不进 Git、不发服务器。
2. 每次只重出一栋或一个片区，不一次性全量重跑。
3. 新旧瓦片共存，按楼栋替换。
4. 切片在本地完成，服务器只读。
5. 每次发布带瓦片数、总字节、根变换、LOD 范围、控制点残差。

## 5 服务器侧

发布目录新增：

```text
reality/
  tileset.json
  tiles/
    ...
  manifest.json
```

Nginx：

```nginx
location /reality/ {
    alias /srv/cdut3d/current/reality/;
    try_files $uri =404;
    expires 1h;
    add_header Cache-Control "public, max-age=3600, must-revalidate";
}
```

要求：

- 支持 HTTP/2。
- 对 JSON 开 gzip，对 GLB/b3dm 按实际压缩效果测试。
- ETag + 304，避免重复下载。
- 服务器不记录原片路径。

## 6 前端接入顺序

### P0 适配层

- 引入 `3d-tiles-renderer`。
- 加载一个楼的 `tileset.json`。
- 不改变现有白模、楼层、房间逻辑。
- 增加“实景层”开关。

### P1 配准

- 增加 `building_anchors`。
- 用控制点对齐。
- 输出配准报告。

### P2 体验

- 远近景淡入淡出。
- 实景层与剖切互斥。
- 首屏优先白模，实景延迟加载。
- 低配设备自动关闭实景。

### P3 本地再生产

- RCNode 批处理。
- Py3dtiles 切片。
- 自动质检与发布。

## 7 验收指标

| 指标 | 目标 |
|---|---|
| 首屏 | 白模先出现，不等待实景 |
| 配准 | 控制点有实测残差；没有则标“未量到” |
| 内存 | 长时浏览不持续上涨 |
| 失败回退 | 瓦片 404/解析失败时白模仍可用 |
| 可追溯 | tileset、瓦片、控制点、发布清单同版本 |
| 权限 | 原始影像和位姿不进入公网目录 |

## 8 风险

1. 照片瓦片的阴影、噪点和接缝会让“风格化”变成“照片加滤镜”。
2. 48,701 块瓦片的首屏、内存和后端 IO 需要专门压测。
3. 3D Tiles 与 EPSG:4544 的坐标对齐是最大技术风险。
4. RealityCapture 1.5 的长期授权需核验；长期建议评估 RealityScan 2.2。
5. 浏览器 WebGL 显存有限的设备需要降级路径。

## 9 结论

这条路线可以落地，但应分两步：

1. **先让一栋楼的 3D Tiles 在独立对照页跑起来**，量首屏、内存、配准。
2. **再把实景层接入现有 Three.js 场景**，不重写白模、房间和判据。

不要先做全校区 48,701 块瓦片的“大而全”改造；先拿一栋楼形成可验收闭环，再按栋复制。

## 10 本地实景定位台（2026-10-21）

现有 2024 倾斜摄影 3D Tiles 已能在本机直接浏览。为了先把楼栋在实景中的位置量准，
新增本地定位页：

```text
python tools/reality_locator_server.py
http://127.0.0.1:8151/
```

页面加载 `tileset_shallow.json` 作为定位用低 LOD 入口，用户把楼栋主体对准屏幕中心后，
点击「记录当前中心点」。后台同时保存：

- WGS84 经纬度与椭球高；
- EPSG:4544 平面坐标；
- 相机 heading / pitch / range；
- 楼栋编号与记录时间。

记录文件：`过程/_scratch/reality_locations.json`。该文件只含人工定位结果，不包含原始影像、
POS、控制点或摄影测量工程。

下一步：把已记录的楼栋位置转换为观察相机，在展示页左下角渲染同步旋转的实景小窗；
在定位数据未验收前，不在服务器端猜测楼栋位置。
